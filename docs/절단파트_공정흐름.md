## 1. 한눈에 보는 전체 공정

```mermaid
flowchart TD
    P["① 호선·블록 등록<br/>Project (ACTIVE)"]
    D["② 도면 업로드 (강재리스트)<br/>DrawingList (CAUTION/REGISTERED)"]
    S["③ 강재 등록<br/>SteelPlan REGISTERED(=화면라벨 '대기')"]
    R["④ 입고처리<br/>SteelPlan RECEIVED(=화면라벨 '입고') + 판번호 SteelPlanHeat (WAITING)"]
    C["⑤ 확정 (일괄/단건)<br/>SteelPlan.reservedFor 채움 → DrawingList (WAITING)"]
    CUT["⑥ 현장 절단 작업일보<br/>CuttingLog STARTED → COMPLETED"]
    DONE["⑦ 완료 연쇄동기화<br/>도면 CUT · 강재 COMPLETED · 판번호 CUT · 잔재 발생/소진 · 블록 완료판정"]
    REM["잔재 관리<br/>Remnant (IN_STOCK)"]
    MATCH["⑧ 강재매칭 → 선별<br/>shipoutMarkedAt 마킹"]
    SHIP["⑨ 외부 출고장 Shipment<br/>강재 SHIPPED_OUT · 잔재 EXHAUSTED"]
    INV["거래명세표 출력"]
    REP["보고서·기성<br/>가동시간·물량 집계"]
    URG["돌발작업 UrgentWork<br/>(정규 도면 무관)"]

    P --> D
    P --> S --> R
    D --> C
    R --> C
    C --> CUT --> DONE --> REM
    R -. 선별 .-> MATCH
    REM -. 선별 .-> MATCH
    MATCH --> SHIP --> INV
    DONE --> REP
    SHIP --> REP
    URG -. isUrgent 절단 .-> CUT
```

**큰 줄기**: 호선 → 도면 + 강재 → 입고 → 확정(도면↔강재 연결) → 절단 → 완료(자동 동기화) → 잔재/출고/기성.
**두 갈래**: 정규작업(도면 기반)과 돌발작업(잔재/긴급 기반)은 같은 작업일보(CuttingLog)를 쓰되 완료 시 동기화 대상이 다릅니다.
**상호배제 축**: 한 강재/잔재는 *절단용(reservedFor)* 과 *출고용(shipoutMarkedAt)* 중 하나로만 — [§6](#6-핵심-불변식-규칙) 참조.

#### 판번호 모델 *(A2 확정)*
판번호(heatNo)는 **철판 1장의 고유 식별자**(주민번호 개념)이나, 시스템은 강재를 두 층으로 분리해서 다룬다:
- **강재목록 `SteelPlan`** = *호선+재질+사양* 단위 재고 (몇 장 있다). 입고·확정·소진은 여기서 **사양 단위**로 일어남.
- **판번호목록 `SteelPlanHeat`** = 판번호들의 풀 (사양에 느슨하게 묶임, FK 직접연결 없음).

입고/선별 단계에선 판번호를 일일이 확인할 수 없으므로 **강재 1장 ↔ 판번호를 직접 묶지 않는다.** 대신 **절단/외부출고 시점**에 담당자가 판번호를 확인해 "사용"으로 잡으면 → ① 강재목록에서 그 사양 1장이 소진(COMPLETED/SHIPPED_OUT) + ② 판번호목록에서 그 판번호가 CUT/SHIPPED 처리. **외부출고 때만 판번호 확인이 필수**이고, 내부 절단은 사양 단위로 흐른다.

**절단완료 후 판번호 추적 기록 위치** (밀시트 역추적 근거 → B2):
- `DrawingList.heatNo` — 그 도면에 쓰인 판번호
- `SteelPlan.actualHeatNo`/`actualVesselCode`/`actualDrawingNo` — 그 강재 1장이 어디에 쓰였는지
- `SteelPlanHeat.status = CUT` — 그 판번호가 절단됨
- `CuttingLog` — 절단 실적(작업자·일시·도면)

## 4. 상태 전이도 (엔티티별)

### 4-1. 강재 SteelPlan (원판)
```mermaid
stateDiagram-v2
    [*] --> REGISTERED: 강재 등록
    REGISTERED --> RECEIVED: 입고처리(receivedAt)
    RECEIVED --> ISSUED: 절단장 투입(reservedFor 필요)
    RECEIVED --> COMPLETED: 절단완료(동일사양 FIFO 1장)
    ISSUED --> COMPLETED: 절단완료
    RECEIVED --> SHIPPED_OUT: 외부출고(Shipment)
    COMPLETED --> RECEIVED: 절단취소(작업일보 삭제)
    SHIPPED_OUT --> RECEIVED: 출고장 취소 (선별 유지/해제 선택)
    ISSUED --> RECEIVED: 투입취소
```
- `RECEIVED` 상태에서 두 가지 *선점*이 갈립니다: `reservedFor`(절단확정) ↔ `shipoutMarkedAt`(출고선별). **둘은 상호배제** ([§6](#6-핵심-불변식-규칙)).
- **출고취소 후의 선점 상태** *(2026-07-25, R16)*: 출고장 취소는 두 갈래다(취소 버튼 → 선택 모달 → `cancel` API `keepSelection`). ① **기본(선별 유지)** — `RECEIVED` 로 되돌리면서 `shipoutMarkedAt` 을 **재생성**하고(출고 확정 때 null 로 지워지므로 **선별일이 취소 시각으로 갱신**된다), 판번호는 `ShipmentItem.heatNo` 스냅샷에서 복원, `shipoutCancelledAt` 를 찍는다 → 자재는 **출고선점 풀에 그대로 남아** 절단 확정·소진·도면 매칭·절단투입 풀에서 계속 제외(R1). ② **선별 해제** — 마킹 3종을 모두 null 로 지워 강재전체목록 입고 재고로 완전 복귀. 단 ①에도 **예외**: 원래 선별된 적 없는 자재(현장직접출고 `adHocFromField=true` 이면서 `shipoutLabel`·`originShipoutLabel` 둘 다 없음)는 기본 모드여도 마킹을 새로 만들지 않고 해제한다(절단 풀에서 조용히 빠지는 것 방지, `cancel/route.ts:89`). **화면**: 강재전체목록 확정정보에는 여전히 빨간 `{라벨} 선별` 로만 보이고, **취소 흔적(주황 `출고취소` 배지)은 선별목록 탭에서만** 보인다. 그 자재를 절단에 쓰려면 **선별 취소가 별도로 필요**하다.
- 절단 완료 시 동일 사양(호선+재질+두께+폭+길이) **RECEIVED/ISSUED 1장만** COMPLETED로 소진 (도면 1 : 원판 1).
- **표기 주의** (2026-07-14): enum 값과 화면 라벨이 다름 — `REGISTERED`=**대기**, `RECEIVED`=**입고**, `ISSUED`=**투입**, `COMPLETED`=**절단**, `SHIPPED_OUT`=**외부**. 코드/DB 는 enum 값 그대로 유지, UI 만 라벨 변경.

## 5. 완료 / 삭제 연쇄동기화 (핵심)

절단 **완료**(`PATCH action=complete` 또는 사무실 백필)와 **삭제**(`DELETE`)는 한 트랜잭션으로 여러 테이블을 동시 갱신합니다. 공용 로직: `lib/cutting-complete.ts` (`applyCuttingComplete` / `applyCuttingRestore`).

```mermaid
flowchart TD
    A["절단 완료 (CuttingLog → COMPLETED)"] --> B["도면 DrawingList → CUT"]
    A --> C["강재 SteelPlan 1장 → COMPLETED<br/>(이 블록 확정분만 · FIFO 1장, 없으면 스킵 — R3)"]
    A --> D["판번호 SteelPlanHeat → CUT<br/>(selectedHeatId 정확 소진 R13, 없으면 호선우선→무관 폴백 R14)"]
    A --> E["등록잔재 사용 시 → EXHAUSTED<br/>발생 등록잔재에 판번호 전파"]
    A --> F["여유원재(SURPLUS) 사용 시 → EXHAUSTED 소진<br/>+ 실물 판번호 기록(없으면 SteelPlanHeat 신규 CUT 생성)"]
    A --> G["돌발이면 연결 잔재 → EXHAUSTED"]
    B & C & D & E & F & G --> H["블록 완료판정 syncProjectStatus<br/>(모든 도면 CUT → Project COMPLETED)"]
```

- **삭제**는 위를 전부 역방향 복원 (CUT→WAITING, COMPLETED→RECEIVED, 판번호 CUT→WAITING, 잔재 EXHAUSTED→IN_STOCK, 잔재 heatNo→null).
- 잔재(등록/현장) 사용 절단은 정규 강재(SteelPlan)를 건드리지 않습니다(상호배제). **여유원재(SURPLUS)는 잔재 자체를 EXHAUSTED 로 소진하고 실물 판번호를 추적**한다(§9 B1 정정 — 최초 문서의 "IN_STOCK 유지"는 코드 오독이었음).
- **등록잔재 생성 시점 주의** *(N18, 2026-07-15)*: 등록잔재(REGISTERED type)는 **도면 업로드 시점**에 `remnantsData` 로 미리 `IN_STOCK` 생성됩니다. 절단 완료로 잔재가 자동 생성되는 것이 아니라 이미 존재하는 잔재에 **heatNo 만 propagate** 됩니다 (밀시트 역추적 근거). 사용자 관점에서 "아직 안 잘랐는데 잔재 재고에 보임" 은 정상 (B6 결정 참조).
- **여유원재(SURPLUS) 절단 취소 주의**: 절단 시 `SteelPlanHeat` 을 신규 생성했다면(원판 매칭 heat 이 없던 경우) 취소 시 그 heat 은 WAITING 복원이 아니라 **완전 삭제**된다(`autoCreatedFromSurplusCut` 마커) — 실물 원판이 IN_STOCK 으로 되살아나므로 판번호만 유령으로 남지 않게.

| 절단보고서 | 기간 + 호선·블록·재질·두께·폭·길이 | SSR `q=1` 플래그. 결과에만 엑셀·인쇄 |
| 강재전체목록 | 호선·재질·두께·폭·길이 + **상태(칩 다중) · 보관위치 · 확정정보 · 입고일/선별지시일/출고일 기간** *(2026-07-25 확장)* | 호선 칸은 등록 호선 드롭다운(체크 다중선택) |
| 판번호 리스트 | 판번호·호선·재질·두께·폭·길이 | |
| 프로젝트 호선/블록 | 호선→블록 드롭다운 + 진행중만 | 폴더트리 폐지, 뷰토글로 강재리스트↔BOM |

- **입력 규칙**: 한 칸에 **쉼표로 여러 값 = OR**, **칸끼리는 AND**. 텍스트(호선·재질·위치·확정)는 부분검색(`contains`, 대소문자 무시), 숫자(두께·폭·길이)는 정확일치(`in`).
- 검색 패널과 **컬럼 드롭다운 필터는 공존**한다 — [조회]는 패널이 소유한 컬럼만 갱신하고 나머지 드롭다운 필터는 보존한다.
- [전체 보기] 는 조건을 무시하고 전량 조회하는 비상구. [초기화]는 패널 입력·부분검색·컬럼필터를 모두 비운다.

## 12. 외부 강재 출고 (선별지시 / 출고장)  *(절단과 별개 분기)*

절단을 거치지 않고 **원판(SteelPlan)·잔재(Remnant)를 사외로 출고**하는 흐름. 깊은 구현 상세는 `docs/shipout-implementation.md` 참조.

### 선별지시 ≠ 출고장 (두 행위 분리)
| 구분 | **선별지시(Selection)** | **출고장(Shipment)** |
|---|---|---|
| 의미 | "골라내라" 준비/예약 | 실제 사외 출고(거래명세표 발행) |
| 강재 상태 | 입고(RECEIVED) 유지 | 외부(SHIPPED_OUT) |
| 판번호 | WAITING 유지 | SHIPPED |
| 마킹/표시 | `shipoutMarkedAt` + 빨강 "선별" | status 전환 + 빨강 "출고" |
| 되돌리기 | 선별 취소(unmark — 마킹·라벨 모두 삭제) | 출고 취소 — **2모드**(선별 유지=기본·권장 / 선별 해제). 자재 상태 복원(RECEIVED / 판번호 WAITING, 자동생성 판번호는 삭제)은 공통, 선별 마킹 처리만 갈림 (R16) |

순서: **선별(준비) → 출고장(실제 출고)**. 선별만 하고 나중에 출고장, 또는 선별 없이 바로 출고장도 가능.

> **예외: 흐름 ④ 현장직접출고** (2026-07-14) 는 **선별 단계를 완전히 건너뜀**. `shipoutMarkedAt`·`selectionPrintedAt` 둘 다 채워지지 않으며 유일한 흔적은 `ShipmentItem.adHocFromField=true`. R1(절단↔출고 상호배제) 은 `reservedFor` 로만 유지되며, 사무실이 선별해둔 자재도 후보에 노출됨(정책상 의도 — [§10 이슈 I1](#10-검토-결과--구현-backlog-9-확정) 참고).

### 4대 업무 흐름 (2026-07-14 확장)
- **① 입고확인+선별**: 사양 엑셀 → 매칭(모든 상태 표시) → 필요 자재 선택 → 선별지시서 출력(확정정보 "선별")
- **② 바로출고**: 현장 판번호 → 출고등록(판번호 매칭) → 차분 출고증(선별 없이 바로) — *사무실 PC 흐름*
- **③ 선별 후 출고**: 소요 사양 → 선별 → 선별 풀 → 현장 판번호 확인 → 차분 구성 → 출고증
- **④ 현장직접출고** *(2026-07-14 신설, 커밋 a6861925)*: /field/shipout → [현장직접출고] 탭 → 판번호 스캔(또는 사양 폴백) → GET `/api/steel-plan/shipout-field-adhoc` → **shipoutMarkedAt 무관**하게 `status=RECEIVED + reservedFor=null` 원판 후보 노출 → 담기 → 카트(같은 세션스토리지, [출고담기] 탭과 공유) → 출고장 생성. 담긴 자재는 `ShipmentItem.adHocFromField=true` 감사 태그. 판번호가 시스템에 없으면 새 SteelPlanHeat(autoCreatedFromShipment=true, status=SHIPPED) 자동 생성.
  - **표준 흐름과의 차이**: shipout-mark 단계를 건너뛰므로 `shipoutMarkedAt` / `selectionPrintedAt` 둘 다 채워지지 않음. R1(절단↔출고 상호배제)은 `reservedFor` 로 유지.
  - **카트에 자재 있을 때 다이얼로그**: [현재 카트에 추가 = 같은 거래명세서] vs [카트 비우고 새로 담기 = 새 거래명세서]
  - **감사 표시**: 카트 펼침 목록, 출고장 상세 자재 행, 거래명세표 인쇄에 `현장직접` cyan 배지 노출

5. 같은 판번호가 여러 규격에 등록된 경우(수입재) ①은 그 규격들을 **전부** 후보로 본다. ②는 대표 규격 + `otherSpecs` 안내(②의 사양 그룹핑 키에는 호선이 포함(field-adhoc:162)돼, 규격 같고 호선만 다르면 `otherSpecs` 로 안내됨 — R12 와 어긋나는 잔여 지점. 현재 다중사양 판번호 0건이라 무해).

- `notReceivedCount > 0` → "이 규격 N장은 이미 절단/출고 처리됨"

### 유령 판번호 방지 — 출고 확정 시 판번호 처리  *(2026-07-22, `ec7ba70e`)*

`POST /api/shipments` 의 판번호 분기는 세 갈래다. **잘못 설계하면 같은 판번호가 두 줄로 늘어나고 실물 추적이 끊긴다.**

| 경로 | 조건 | 동작 |
|---|---|---|
| **매칭됨** | `heatNo 有` + `manualHeatNo=false` + `steelPlanHeatId 有` | 그 heat 을 `WAITING → SHIPPED` 원자적 전환. 이미 바뀌었으면 롤백 |
| **직접입력** | `manualHeatNo = true` (steelPlanHeatId 보다 우선) | ① 같은 호선에서 `heatNo`+규격 WAITING 조회 → ② 없으면 **호선 무관**으로 재조회 → ③ 그래도 없으면 **호선 무관 중복검사**(이미 CUT/SHIPPED 면 트랜잭션 롤백 + 사유 메시지, 응답 **500** — 409 는 발번 충돌 P2002 전용이라 성격 다름) → ④ 통과 시에만 신규 생성(`autoCreatedFromShipment=true`) |
| **미입력** | 판번호 없음 | 규격 WAITING 1장 FIFO 소진 — 같은 호선 우선, 없으면 타 호선(route.ts, 2026-07-23 호선 무관화). 진짜 판번호 미상이면 통과 |

> ⚠ **분기 우선순위**: `manualHeatNo=true` 가 `steelPlanHeatId` 보다 우선한다. `heatNo` 가 빈 채 `heatId` 만 오면 어느 갈래도 안 타 판번호가 WAITING 으로 남는다(현재 UI 미도달 — 신규 호출부 추가 시 주의).
>
> **왜 직접입력의 ②③이 필수인가** — 이게 없으면 옆 호선 철판을 출고할 때 재고 판번호를 못 찾고, 중복검사도 통과해서, **잘못된 호선으로 같은 판번호를 새로 만든다.** 진짜 판번호는 WAITING 으로 남아 나중에 절단이나 다른 출고에 다시 소진된다.

**입구 방어도 같이 있어야 한다** (하나라도 빠지면 위 경로로 떨어진다):
- 후보 목록(`heat-match`·`shipout-match`)이 호선으로 잠겨 있으면 유용 강재 판번호가 **절대 안 뜨고** 반드시 손입력이 된다 → 호선 잠금 금지 *(✅ 둘 다 해제됨)*
- 후보 조회 실패를 `catch {}` 로 삼키면 **멀쩡한 상황에서도 목록이 비어** 손입력이 된다 → 반드시 화면에 노출 *(✅ shipout-bar 는 `optErrors → heatOptError` 로 노출)*
- 엑셀 업로드는 판번호 미매칭을 `HEAT_NOT_FOUND` 로 **구분해 표시**하고 기본 담기 제외 + 명시 동의 체크박스로만 포함 (예전엔 삼항식 양쪽이 모두 `MATCHED` 라 실패가 보이지 않았음)
- 출고 확정 손입력 조회는 **R15 정규화 폴백 적용** *(2026-07-23)* — `SUS-4`↔`SUS4` 표기차여도 기존 판을 찾아 신규생성으로 안 떨어진다.

**현재 실제 피해는 0건이다** — `autoCreatedFromShipment=true` 판번호는 0건(측정 시점). 위는 전부 잠재 경로이며, 이 방어들이 그 상태를 유지시킨다.

### 절단 ↔ 출고 상호배제 = R1 (§6)
`reservedFor`(절단확정)·`shipoutMarkedAt`(출고선별) 둘 다 status를 RECEIVED로 유지하므로, 각 풀에서 **반대편 필드를 명시 제외** + 쓰기 경로 **409 가드**로 상호배제. (Phase 0~3 구현 완료: 커밋 cd2a7c5f·0e987ca4·2dd1165e·c7f33931)

**강재(SteelPlan) 층에서 이미 배타적이다** — 2026-07-22 실측: 입고 재고가 있는 규격 1417종 중 확정과 선별이 동시에 걸린 규격은 **2종**(각 1장씩, 여유 16·4장). 절단은 확정분만 소진하고([cutting-complete.ts](../lib/cutting-complete.ts) `reservedFor: { in: allowedReservedFor }`), 선별은 확정분을 제외한다([shipout-match](../app/api/steel-plan/shipout-match/route.ts) `reservedFor: null` + `RESERVED_FOR_CUTTING` 안내).

> **판번호 층에는 방어가 없고, 있어서도 안 된다.** `heat-options` 에 "선별된 판번호 제외" 로직이 있으나 제외 기준이 `shipoutHeatNo ≠ null` 인데 현재 선별 흐름(선별지시 → 현장 선별 → 판번호 매칭)은 선별 시점에 판번호를 모르므로 이 값이 항상 null → **실질 dead code**. 이를 "수량만큼 FIFO 로 가리기" 로 대체하자는 제안은 **기각**(2026-07-22): 어느 실물이 절단용이고 어느 것이 출고용인지 판번호에 안 적혀 있으므로 수량으로 추측해 가리면 **절단팀이 손에 든 진짜 판번호가 가려져** 오히려 오기입을 유발한다. 강재 층 배타성으로 충분하다.

### 원판 + 잔재 통합 출고 (2026-06-20, adb9e77f)
선별 목록에 **[잔재 추가]** 로 잔재(여유/등록/현장)를 원판과 **같은 출고장**으로 함께 출고.
- **현장 출고관리(/field/shipout) 출고담기**: '잔재 출고' 체크박스 — 해제=판번호(원판), 체크=**잔재번호**로 출고담기(2026-06-26). 잔재번호로 IN_STOCK+미확정(reservedFor null)+미출고 잔재를 찾아 담음(선별 마킹 불필요, 출고 시 EXHAUSTED). 잔재번호는 대문자·숫자·특수문자 허용.
- `ShipmentItem` = `steelPlanId` **XOR** `remnantId`.
- 출고 잔재 불변식: **IN_STOCK + reservedFor=null** (PENDING·절단확정·EXHAUSTED 출고 차단).
- 잔재 lifecycle: 선별=`shipoutMarkedAt` 마킹 / 출고=EXHAUSTED + **마킹 null 정리** / 취소=IN_STOCK 복원 + `keepSelection` 규칙(R16).
  - ⚠ **취소 시 원판과 비대칭** *(2026-07-25)*: 잔재 복원에는 원판의 현장직접출고 예외가 없다. `keepSelection`(기본 true)이면 무조건 `shipoutMarkedAt: rem.shipoutMarkedAt ?? new Date()` — 출고 확정 때 마킹이 이미 지워졌으니 좌변은 항상 null → 실질 **항상 새 마킹**. 결과: **잔재번호로 바로 담아 출고한(선별한 적 없는) 잔재**도 취소하면 선별목록에 새로 등장하고 절단 확정·소진에서 빠진다(`keepSelection=false` 면 미발생). `Remnant` 에 `shipoutCancelledAt` 컬럼이 없어 주황 배지 경고도 없다. 원판 조건을 그대로 복사해도 해결되지 않는다(잔재 담기 경로가 `adHocFromField` 태그를 안 붙여 항상 false) — ① `Remnant.shipoutCancelledAt` ② 출고 전 선별 여부 스냅샷이 함께 필요. 현재는 감수(§15-4).
- **거래명세표 "잔재번호" 컬럼**(2026-07-01, 3f5b4576): 기존 "절단예정일" 컬럼 대체. 잔재 출고 시 `ShipmentItem.remnantNo`(출고 시점 잔재번호 스냅샷)를 서버측에서 채워 명세표에 읽기전용 표기(원판 출고는 공란). 잔재번호는 불변 식별자라 스냅샷이 안전.
- **카트 개별 취소**(2026-07-01): 출고 카트를 쓰는 **모든 곳**에서 담은 자재를 1건씩 취소(`cart.remove`). 기존엔 "비우기(전체)" 만 있었음.
  - **현장**(field-shipout, 2026-07-14 이후 3탭 모두 동일 카트 공유): 담기/현장직접출고 탭 하단 카트바의 "N건" → 담은 목록 펼침 + 각 자재 🗑️.
  - **PC**(강재전체목록·선별목록 공용 `shipout-bar`): 하단 카트바 "출고 카트" 클릭 → 담은 목록 펼침 + 🗑️. "출고장 만들기" 모달의 미배차 자재 테이블에도 삭제 열 추가. (강재전체목록 "출고등록" 모달은 카트 담기 전 staging 목록이라 자체 삭제가 이미 있었음 — 별개 단계.)

### 취소된 출고장 영구 삭제 *(2026-07-14 신설)*

### 판번호 = 사양 매칭 추적용 (물리 지목 아님)  *(N21 재언급, 2026-07-15 / 2026-07-22 보강)*
§3 A2 정책 재요약 — 판번호(heatNo) 는 원판 1장의 고유 식별자 의미이지만, **시스템 상 강재(SteelPlan) 와 판번호(SteelPlanHeat) 는 느슨 연결**(FK 없음, 규격으로만 이어짐). 강재매칭이 heatNo → spec → SteelPlan(FIFO oldest) 로 임의 판 반환. 같은 사양이 여러 장이면 시스템이 고른 판재와 사용자 손의 물리 판재가 다를 수 있음. 재고 정합성은 사양 단위 카운트로 정확.
- **출고 시**: 강재매칭 결과에 판재 입고일/위치 표기 → 사용자가 물리 판과 대조 가능
- **매뉴얼 안내**: 필요 시 사용자 교육에 "판번호는 사양 추적, 물리 판 지목 아님" 을 명시.

> **이 느슨 연결이 만드는 두 가지 성질** (2026-07-22 정리 — 버그가 아니라 모델의 귀결이다)
> 1. **호선은 실물을 구분하지 않는다.** 강재 행(SteelPlan)에는 호선이 붙지만 판번호는 규격 풀에 속한다. 그래서 판번호 조회에 호선을 걸면 안 된다(R12). 실측(2026-07-22)으로 출고담기 대기판번호의 약 31%가 이 잠금 때문에 막혀 있었다(§15-1).
> 2. **호선별 장수 정합은 어긋날 수 있다.** "1022 원판을 출고했는데 1023 판번호가 소진" 이 정상 동작으로 발생한다. **총량은 항상 맞고 호선별 배분만 흔들린다.** 기성이 블록·부재 중량 기준이면 영향 없으나, 호선별 강재 소비량으로 정산한다면 별도 검토가 필요하다(미결).

## 15-6. 정합성 진단 H — 완료 블록 잔여 확정 *(2026-08-18 신설)*

현장이 **두 번** 같은 말로 신고한 유형: "블록 절단이 이미 끝났는데 강재전체목록에는 아직 확정으로 남아 있다."
(2026-07 `KYTS-1022/S60PS` 11장, 2026-08 `KYTS-1022/S70PS` 1장)

**기존 진단이 왜 못 잡았나 — 실측 G 포착률 0/1**
| 판정 | 놓친 이유 |
|---|---|
| **G** 유령 확정 | `reservedFor` 블록의 **도면이 존재하는지**만 본다 → 도면은 멀쩡히 있으니 통과 |
| **D** 사양 수량 불일치 | 사양 **총량** 비교라 다른 블록 잔여와 상쇄되면 차이가 0 |

**H 판정** — `reservedFor` 가 있고 상태가 재고(REGISTERED/RECEIVED/ISSUED)인 철판 중,
그 블록의 `DrawingList` 가 1행 이상이면서 **전부 `CUT`** 인 것.
- `reservedFor` 는 `"호선/블록"` · `"블록"` 두 형태 → 후자는 자기 호선 키 우선, 없으면 동명 블록 전체가 **모두 완료일 때만** 지적(보수적)
- 도면이 아예 없으면 제외(그건 G 의 영역)
- `hint` — 그 블록에 **같은 사양 도면이 있으면** "소진 누락 의심", 없으면 "확정 오배정 의심"

**A(중복 절단)와의 관계** — 이번 1건의 근본 원인은 작업일보 2건(CNK001·CNK002)이 **같은 판번호**(`B56927905`)를 기록해 철판 1장이 소진되지 않은 것이라 A 도 잡는다. 그러나 H 는 **원인이 아니라 결과**를 본다 — 소진 누락·확정 오배정·완료처리 누락 등 원인이 무엇이든 "끝난 블록에 재고가 남았다"는 사실 하나로 걸린다. 현장이 실제로 쓰는 표현과 같은 판정이라 신고→확인 경로가 짧다.

**재발 원인까지 추적 — 수동 교정이 [새로고침]에 취소되고 있었다**
이번 1건은 **2026-07-21 에 이미 교정했던 바로 그 철판**이다(`ghost-fix-2026-07-21-undo.json` 의 4장 중 유일하게 살아있는 행). 왜 되돌아왔나:
- 유령 확정 사후정리 같은 **손 교정**은 `status`·`issuedAt` 만 세팅한다 — 소진 근거가 판번호가 아니라 사람 판단이라 `actualHeatNo` 는 비어 있다.
- 그런데 `steel-plan/sync` 에 `COMPLETED + actualHeatNo = null → RECEIVED` 규칙이 있었고, 이건 **강재입고관리 [새로고침] 때마다 자동 실행**된다.
- 즉 **교정이 새로고침 한 번에 조용히 취소**됐다. 되돌린 흔적도 안 남는다.

→ 그 규칙에 `issuedAt: null` 조건을 추가했다. `issuedAt` = "절단완료 처리를 실제로 거쳤다"는 흔적이므로, 있으면 정상 완료로 보고 남긴다. 잘못된 건이면 진단 H·D 가 별도로 띄운다.
> **손으로 데이터를 교정할 때 규칙**: 절단완료로 바꾸려면 `issuedAt` 을 반드시 함께 채울 것. 안 채우면 다음 새로고침에 되돌아간다.

### 15-6b. sync 가 손 교정을 취소하고 있었다 — 판번호까지 *(2026-08-18 실측)*

§15-6 에서 강재(SteelPlan) 쪽 되돌리기(`actualHeatNo=null → RECEIVED`)를 막았는데, **판번호에도 같은 규칙이 있었다.**

`steel-plan/sync` 규칙 ③ — `CUT 판번호 중 heatNo 가 완료 작업일보에 없으면 → WAITING + cutAt 삭제`.
근거를 **손입력 문자열(`CuttingLog.heatNo`)로만** 찾는 게 문제다. 그 문자열은 틀릴 수 있고(옆 호선 판번호 오기),
틀리면 진짜 소진된 판이 "근거 없음"이 되어 [새로고침] 한 번에 되돌아간다.

> **실증**: 2026-08-18 오전 교정한 `B56848103` 이 같은 날 안에 `WAITING`·`cutAt=null` 로 되돌아갔다.
> `status: WAITING, cutAt: null` 을 쓰는 코드는 이 규칙뿐이다.

**조치 — `consumedHeatId` 를 근거로 인정**
스키마가 이미 정답을 갖고 있었다: `consumedHeatId` = *"절단완료 시 **실제로** 소진한 판번호 id — selectedHeatId(의도)와 다를 수 있음"*.
손입력 문자열이 틀려도 실제 소진 판은 이 필드로 정확히 가리킬 수 있다.
- **sync ③** — `consumedHeatId` 로 지목된 판은 되돌리지 않는다
- **sync ①** — 근거 heatNo 집합에 `consumedHeatId` 가 가리키는 판의 heatNo 도 포함(`actualHeatNo` 대조용)
- **진단 C(유령 절단)** — 같은 이유로 `consumedHeatId` 링크가 있으면 근거 있음으로 인정(안 그러면 교정분이 영구히 '유령'으로 뜬다)

**데이터 교정 2건** (`scripts/fix-consumed-links.mjs`, undo JSON 동반) — **작업일보의 `heatNo` 문자열은 그대로 두고** 실제 소진 판만 연결:
| 작업일보 | 기록된 heatNo | 실제 소진 | 추가 조치 |
|---|---|---|---|
| `S50PS/CNX039` | `PP79328103` (KYTS-1023 · SHIPPED, 오기) | `B56848103` | 판번호 → CUT |
| `S70PS/CNK001` | `B56927905` (CNK002 와 중복 기록) | `B56918601` | 판번호 → CUT, 철판 → 절단완료 |
교정 후 진단 **H = 0**.

> ⚠ **배포 순서 주의** — 이 데이터 교정은 **새 sync 가 배포된 뒤에만 유지된다.** 구 코드에서는 [새로고침] 한 번에 다시 되돌아간다(`scripts/diag-sync-revert.mjs` 로 신·구 규칙 비교 확인 가능).
> **손으로 절단완료를 교정할 때 규칙**: 강재는 `issuedAt` 을, 판번호는 작업일보의 `consumedHeatId` 를 반드시 함께 채울 것. 안 채우면 sync 가 되돌린다.

**부가** — `totals` 에 활성/아카이브 분리 집계 추가(`activeSteelPlans`/`archivedSteelPlans` 등). 화면 목록은 아카이브를 제외하는데 진단은 전량을 세므로 숫자가 달라 보이던 것을 §16-6 감수 항목에서 해소.

## 16. 아카이브(숨김/복원) — 전면 리뷰 & 수정 *(2026-08-18)*

현장 신고 "복원했다가 다시 아카이브하면 수량이 안 맞는다 / 강재전체목록과 판번호 목록 수량 차이가 크다" 에서 출발. 5관점 리뷰 60건 제기 → 적대적 반증으로 **41건 확정**. 1·2단계 조치 완료.

### 16-1. 아카이브의 정의 (사용자 이해 = 정확)
**삭제가 아니라 숨김이다.** `SteelPlan.archivedAt` / `SteelPlanHeat.archivedAt` 에 시각을 찍으면 활성 목록에서 빠지고 아카이브 화면에서 조회·복원된다. 행은 지워지지 않는다.
- ⚠ **기간 입력칸은 조회 전용**이다. 실행 범위는 오직 상단 "완료·출고된 지 N개월 이상". 두 칸이 붙어 있어 오해가 잦아 화면에 명시 문구를 넣었다(2026-08-18).

### 16-2. 근본 원인 — 판정축이 스스로를 오염시켰다 *(신고 증상 본체)*
대상 판정이 터미널 날짜(`cutAt`/`shippedAt`/`issuedAt`) 결측 시 **`updatedAt` 폴백**을 썼는데, 아카이브(`archivedAt=now`)도 복원(`archivedAt=null`)도 Prisma `@updatedAt` 때문에 `updatedAt` 을 '지금'으로 갱신한다.
> **날짜를 보고 판단하는데, 판단하는 행위 자체가 그 날짜를 망가뜨린다.**

폴백 의존 레코드는 왕복 한 번에 판정에서 이탈하고, 왕복할 때마다 설정 개월 수만큼 뒤로 밀린다(영구 아님 — 단 왕복 주기가 설정보다 짧으면 사실상 영구).

**실측(2026-08-18)** — `cutAt` 결측 CUT 판번호 361건 전부가 `updatedAt = 2026-08-17 02:10:42.602` (밀리초까지 동일 = 단일 일괄 조작 흔적). 결과 **강재 3,341 vs 판번호 2,980 = 360 차이** ≒ 이탈 361건.

**조치** — ① 361건 `cutAt` 을 작업일보에서 백필(`scripts/backfill-heat-cutat.mjs`, **raw SQL 로 써서 `updatedAt` 보존**, 근거 361/361 = heatNo+사양 매칭) ② **`updatedAt` 폴백 자체 제거**. 결과 **판번호 3,384 = 강재 3,384, 격차 0**. 판정축이 전부 불변 업무일자가 되어 **왕복 멱등이 구조적으로 보장**된다.
> 폐기한 대안: `updatedAt` → `createdAt` 폴백. 2년 전 입고·어제 절단한 판이 즉시 대상이 되어 반대로 틀린다. 결측을 0으로 만들고 폴백을 없애는 것이 정답.

### 16-3. 불변식 A1 — 아카이브된 것은 반드시 종료 상태
`archivedAt IS NOT NULL` ⇒ heat ∈ {CUT, SHIPPED} / plan ∈ {COMPLETED, SHIPPED_OUT}.

깨지면 **유령 재고**가 된다 — 상태는 재고인데 숨김이 남아 강재전체목록·판번호리스트·아카이브 어디에도 안 보이면서 **소진은 계속된다**(화면 재고는 그대로인데 실가용만 줄어듦). §13 S60PS 유령 확정과 같은 계열.

터미널 상태에서 빠져나오는 **모든** 전이가 `archivedAt: null` 을 함께 써야 한다. 조치한 7곳:
| 파일 | 경로 |
|---|---|
| `lib/cutting-complete.ts` | `applyCuttingRestore` 4곳 (정확복원 / SURPLUS heat / 일반 heat 1장 / SteelPlan RECEIVED) |
| `app/api/shipments/[id]/cancel/route.ts` | 원판 SHIPPED_OUT→RECEIVED, 판번호 SHIPPED→WAITING |
| `app/api/steel-plan/sync/route.ts` | COMPLETED→RECEIVED 2곳, CUT→WAITING 1곳 (**강재입고관리 [새로고침] 이 매번 자동 실행**) |

추가 안전망: **아카이브 실행 시 유령을 먼저 자동 청소**한 뒤 아카이브한다(같은 트랜잭션). 실행 결과에 `ghostCleaned` 로 보고.

### 16-4. 숨김 적용 범위 — 목록과 필터의 모집단은 같아야 한다
목록 본문에만 `archivedAt: null` 이 걸려 있고 **필터 선택지 쿼리에는 없어**, 숨긴 값이 드롭다운에 남아 고르면 0건이 나왔다("숨겼는데 왜 여기 있지?"). 조치: `steel-plan/distinct`(15개) · `steel-plan/heat/distinct`(8개) · `steel-plan/vessels` 에 동일 조건 추가.
매칭 노출도 차단: `heat-match`(출고장 판번호 후보 — CUT 도 후보라 명시 필요) · `steel-match/[id]`(강재매칭 상세).
> 소진·매칭 쿼리 대부분은 비종료 상태로 걸러 A1 이 지켜지면 자연 배제된다. A1 이 1차 방어선이다.

### 16-5. 그 밖의 조치
- **삭제 가드**: 호선/배치 단위 삭제가 아카이브분을 경고 없이 영구 삭제하던 문제 → 409 + 건수 안내, `forceArchived` 로만 강행.
- **트랜잭션화**: run·restore 를 `$transaction` 으로. 개별 복원은 `archivedAt: {not:null}` 조건을 걸어 비아카이브 행의 `updatedAt` 을 밀지 않는다.
- **KST 기간 조회**: 컨테이너 TZ 가 UTC 라 `T00:00:00` 이 UTC 자정으로 파싱돼 화면(KST)과 9시간 어긋났다(강재 `issuedAt` 5,297건 중 1,353건 = 25.5% 가 KST 로는 하루 뒤). `+09:00` 명시.
- **월말 버그**: 3/31 에 `setMonth(-1)` 하면 2/31 이 없어 3/3 으로 튀어 아직 1개월 안 된 자재까지 대상이 됐다 → 목표 월 말일로 클램프(`cutoffOf`).
- **강재 basis 분기 신설**: `사용일자`·`출고일자` 를 골라도 강재 탭 결과가 안 바뀌던 문제(강재는 `archivedAt` 외 분기가 없었음).
- **숫자 표기**: 판번호+강재 **합계**를 "판번호 N건"으로 표기하던 것을 분리(`eligibleHeats`/`eligiblePlans`). 현재 아카이브 총량을 화면에 상시 표시(기간 밖 분이 존재조차 안 보이던 문제). 전체 복원에 건수 고지 + 완료 알림.

### 16-5b. 3단계(화면) 조치 *(2026-08-18)*
- **다중 선택 복원** — 체크박스 + 페이지 전체선택(indeterminate 포함). 예전엔 1건씩만 되고 복원할 때마다 1페이지로 튕겨 사용자를 [전체 복원]으로 몰았다. 페이지 리셋 기준을 `rows` 참조 → **조회조건(`queriedKey|search`)** 으로 바꿔 같은 조건 재조회는 페이지를 유지한다.
  - ⚠ **선택은 '지금 필터·검색을 통과한 행'으로 교차해 잘라낸다.** Set 에 그대로 두면 필터를 좁힌 뒤 [선택 복원]이 화면에 없는 행까지 복원한다 — §16-3 유령과 같은 '보이지 않는 것에 손대는' 부류라 같은 원칙으로 막았다.
- **판번호 표 컬럼 정리** — 서버가 항상 빈 값을 보내던 죽은 컬럼 `입고정보>블록` 제거, **상태**·**아카이브일** 신설(강재 탭과 대조 가능해짐).
- **조건 변경 배지** — 기준일·기간을 바꿔도 옛 결과가 남아 새 조건 결과처럼 보이던 문제. `queriedKey ≠ curKey` 면 "조건 변경됨 — [조회]를 다시 누르세요".
- **기준일 없어 제외된 건수 표시** — `basis=사용일자/출고일자` 를 고르면 그 값이 없는 행이 조용히 사라졌다. 서버가 `omitted:{heats,plans}` 로 보고.
- **실행 직전 재조회** — [아카이브 실행]·[전체 복원] 모두 최신 건수를 다시 받아 확인창에 쓴다(탭을 오래 켜두면 미리보기 숫자가 낡음). 0건이면 중단.
- **중복 제출 가드** — `busy` 가 확인창 전 재조회 구간까지 덮도록 확장(연타 시 중복 POST). 복원 경로에도 동일 가드 신설.
- 로드 실패 오류 배너.

### 16-5c. `backfill-issued` 연쇄 *(같은 뿌리)*
`issuedAt` 백필도 근거 없을 때 `updatedAt` 을 썼다. `issuedAt` 이 이제 아카이브 판정의 **유일한 축**이라, 아카이브 왕복 뒤 이 기능을 돌리면 출고일이 "아카이브 누른 시각"으로 영구히 덮어써진다.
- 근거를 ① 같은 사양 CUT 판번호의 `cutAt` ② 같은 사양 완료 작업일보의 `endAt` 로 하고, **없으면 건너뛴다**(`skipped` 로 보고 — 화면에도 표시). 추정치를 박느니 비워 두는 편이 안전하다(비면 아카이브 대상에서 빠질 뿐 화면엔 보인다).
- ②의 호선 키는 `project.projectCode` 가 아니라 **`drawingList.alternateVesselCode ?? projectCode`** — 대체호선이면 강재는 '빌려준 호선'에 있어 작업호선으로 찾으면 영영 못 찾는다(`lib/cutting-complete.ts` 의 effectiveVessel 과 동일 기준).

### 16-5d. 스키마 주석 정정
`SteelPlan.actualHeatNo/actualVesselCode/actualDrawingNo` 주석이 **"레거시 필드 (사용 안 함)"** 로 잘못 달려 있었다. 실제로는 절단완료마다 기록되고 `steel-plan/sync` 가 강재↔작업일보 짝을 찾는 **유일한 연결고리**다. 오해로 삭제되면 상태동기화가 오작동한다.

### 16-7. 기각한 지적 (조사 결과 문제 아님)
- "**복원 대상을 찾는 쿼리에도 숨김 제외를 걸어라**" — 반대다. 아카이브된 행을 찾아야 복원이 된다. 걸면 복원이 통째로 실패.
- "`steel-plan/sync` 가 아카이브를 통째로 되돌린다(high)" — 아카이브 run/restore 는 `archivedAt` 만 쓰고 status·CuttingLog 를 안 건드려 sync 대상 집합을 1건도 늘리지 못한다. 다만 A1 위반은 실재하므로 `archivedAt: null` 은 추가함.
- "전량 로드로 타임아웃" — 실측 DB 14MB, 최악 가정에서도 무영향.
